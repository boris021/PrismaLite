# PrismaLite_Rules_and_Incidents

## 1. Назначение

Документ описывает правила анализа кассовых событий (60+ аналогов Set Prisma), параметры, исключения, алгоритмы проверки и структуру инцидентов. Служит основой для Rules Engine и аналитических модулей.

## 2. Архитектура правил

- Каждое правило имеет: `code`, `category`, `description`, `severity (1-5)`, `params`, `exceptions`.
- Применяются к потоку событий внутри чека или диапазона времени.
- Результат — запись в таблице `incidents`.
- Правила могут быть глобальными или tenant-специфичными.

Категории:
1. Товарные операции (A)
2. Маркировка (B)
3. Чековые операции (C)
4. Оплаты (D)
5. Скидки (E)
6. Кассовые операции (F)
7. Персонал (G)
8. Временные аномалии (H)

## 3. Структура инцидента

```json
{
  "incident_id": 104522,
  "rule_code": "R020",
  "event_id": 992312,
  "check_id": 553244,
  "tenant_id": 12,
  "shop_id": 5,
  "register_id": 3,
  "cashier": "C0021",
  "timestamp": "2025-01-20T15:22:12Z",
  "severity": 3,
  "payload": {
    "sku": "4601234567890",
    "qty_before": 1,
    "qty_after": 3
  },
  "status": "open"
}
```

Статусы: `open`, `in_progress`, `closed`, `false_positive`.

## 4. Перечень правил (выжимка)

### Категория A — Товарные

- **R001 Двойное сканирование**  
  Параметры: `time_window_ms`, `price_tolerance`.  
  Алгоритм: если два consecutives события с одинаковым SKU и Δt < window → инцидент.

- **R002 Уменьшение количества после сканирования**  
  Проверяет `QtyChange` на отрицательное значение, исключая весовой товар.

- **R003 Увеличение количества после скидки**  
  Если после события скидки количество увеличено → инцидент (подозрение на злоупотребление).

- **R004 Отмена товара после подытога**  
  Событие 23 после 90 (`subtotal_passed == true`).

- **R005 Возврат без оригинального чека**  
  Проверяет наличие связанного `check_id` для возвратов.

- **R006 Продажа с нулевой ценой**  
  `price == 0`, исключения: акции, подарочные купоны.

### Категория B — Маркировка

- **R010 Марка не найдена** (`event_code=34`).  
- **R011 Продажа без сканирования марки** — отсутствие 27 перед продажей маркированного товара.

### Категория C — Чековые

- **R020 Длительный интервал между позициями**  
  Параметры: `max_gap_seconds`.  
  Если gap > threshold → инцидент.

- **R021 Чек слишком длинный**  
  Параметры: `max_items`.

- **R022 Чек без подытога**  
  Отсутствие события 90 перед 92.

### Категория D — Оплаты

- **R030 Несоответствие суммы оплаты**  
  Сумма платежей < total.

- **R031 Слишком много частичных оплат**  
  Параметры: `max_parts`.

- **R032 Подозрительная оплата наличными**  
  Параметры: `amount_threshold`, `time_window`.

- **R033 Карта из чёрного списка**  
  Интеграция с blacklist API.

### Категория E — Скидки

- **R040 Скидка после подытога**  
- **R041 Ручное изменение скидки**  
- **R042 Чрезмерная скидка** — params: `discount_percent_limit`.

### Категория F — Кассовые операции

- **R050 Частое открытие денежного ящика**  
  Параметры: `max_per_hour`.

- **R051 Отмена расчёта без причины** (код 91)  
  Параметры: `max_per_shift`.

### Категория G — Персонал

- **R060 Слишком быстрый чек**  
  Δt между позиций < threshold.

- **R061 Частые ошибки сканирования**  
  Кол-во событий 39 за смену > limit.

### Категория H — Временные аномалии

- **R070 Продажи вне смены**  
- **R071 Ночная продажа в нерабочее время**  
- **R072 Обрыв чека** — отсутствие `DOC_END`.

Полный список (60+) поддерживается в справочнике правил и конфигурируется через UI.

## 5. Алгоритм Rules Engine

Потоковая обработка:
```
for event in stream:
    context = context_store.get(event.check_id)
    for rule in active_rules:
        if rule.match(event, context):
            if rule.validate(context):
                create_incident(rule, event, context)
    context_store.update(event)
```

- `context_store`: кэш последних событий по чеку/кассе.
- Поддерживаются sliding window и агрегаты.
- Производительность: задержка обработки < 300 мс.

## 6. Исключения и scope

- Исключения по SKU (whitelist).
- Исключения по кассирам (обучение).
- Исключения по магазинам, времени суток, типу операции.
- Scope правила (`scope`): `{"stores":[1,2], "cashiers":["C01"], "tenants":[null]}`.

## 7. Таблицы и конфигурация

`rules`:

`incidents`:
```

event_id BIGINT

severity INT
status TEXT
payload JSONB
assignee INT
```

## 8. Workflow инцидента

1. **Создание**: Rules Engine или вручную аналитиком.
2. **Назначение**: оператору/аналитику.
3. **Обработка**: просмотр чеков/видео, комментарий.
4. **Закрытие/Эскалация**: статус `closed` или `false_positive`.
5. **Аудит**: все изменения фиксируются в `audit_log`.

## 9. Отчётность и аналитика

- Статистика по правилам (количество, severity).
- Среднее время реакции, доля подтверждённых инцидентов.
- Heatmap по магазинам/кассирам.
- Экспорт в отчёты (см. `PrismaLite_Functional_Spec`).

## 10. Тестирование правил

- Unit-тесты на каждый алгоритм (пример: `tests/rules/test_double_scan.py`).
- Набор тестовых событий (fixtures) для regression.
- Инструмент `rules-simulator` для прогонки исторических логов.
