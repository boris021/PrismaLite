# PrismaLite_Integrations

## 1. Назначение

Документ описывает интеграции PrismaLite с POS-системами (Set Retail, Frontol и др.), форматы данных, pipeline обработки событий и требования к интеграторам. Цель — обеспечить единую модель событий для Rules Engine и аналитики.

## 2. Общая схема

```
[POS Systems] --> [Ingest Gateway] --> [Normalizer] --> [Enricher] --> [Validator] --> [DB Writer]
                                             |                                   \
                                             v                                    -> [Rules Engine]
                                        [Dead-letter / Alerts]
```

- **Ingest Gateway**: HTTP(S) API, file watcher, gRPC, принимает XML/JSON/logs.
- **Normalizer**: приводит события к стандартному JSON формату.
- **Enricher**: дополняет справочными данными (store_id, cashier_id и т.д.).
- **Validator**: проверяет структуру и бизнес-ограничения.
- **DB Writer**: пишет в PostgreSQL (`events`, `checks`).

## 3. Set Retail

### 3.1 Форматы
- XML (Set Prisma): теги `DOC_BEGIN`, `EVENT`, `DOC_END`, `MARK_SCAN`.
- JSON (современные адаптеры).
- Бинарные/структурированные логи (legacy).

### 3.2 Пример XML
```xml
<EVENT>
  <CODE>20</CODE>
  <CASHIER>105</CASHIER>
  <POS>01</POS>
  <TS>2025-01-19T13:20:44</TS>
  <SKU>4601234567890</SKU>
  <QTY>1</QTY>
  <PRICE>249.00</PRICE>
</EVENT>
```

### 3.3 Пример JSON
```json
{
  "code": 20,
  "cashier": "105",
  "pos": "01",
  "ts": "2025-01-19T13:20:44",
  "payload": {"sku":"4601234567890","qty":1,"price":249.00}
}
```

### 3.4 Карта событий (фрагмент)
- 11 — Начало документа.
- 12 — Конец документа.
- 13 — Аннулирование.
- 20 — Добавление позиции.
- 23 — Отмена позиции.
- 25 — Изменение количества.
- 27 — Сканирование марки.
- 38 — Переход на чековую позицию.
- 39 — Сканирование вне чека.
- 50 — Купон.
- 60 — Скидка.
- 70/73 — Платёж (нал/безнал).
- 90 — Подытог.
- 92 — Регистрация чека.
- 100 — Денежный ящик.

Полный список соответствует `События.txt`.

### 3.5 Нормализация Set Retail
Правила:
1. Любая XML-структура → JSON с плоской схемой (snake_case).
2. Все timestamps → UTC (`TIMESTAMPTZ`).
3. SKU/price/qty → строка или decimal по требованиям.
4. Неизвестные события → код 999, payload сохраняется.
5. DOC_BEGIN/DOC_END формируют `check_id`, `check_number`.
6. Hash-схема: `sha256(tenant_id, pos_id, timestamp, event_code, payload)`.

## 4. Frontol

### 4.1 Источники
- Лог-файлы (`*.log`, `*.txt`).
- «Масло» (структурированные файлы).
- API (JSON).

### 4.2 Примеры логов
```
19.01.2025 14:52:01;POS=3;Cashier=12;AddItem;SKU=4601234567890;Qty=1;Price=249
19.01.2025 14:52:05;POS=3;Cashier=12;VoidItem;SKU=4601234567890
19.01.2025 14:52:10;POS=3;Cashier=12;Payment;Type=CARD;Sum=249
```

### 4.3 Пример JSON (API)
```json
{
  "event": "AddItem",
  "ts": "2025-01-19T14:52:01",
  "pos": "3",
  "cashier": "12",
  "payload": {"sku":"4601234567890","qty":1,"price":249}
}
```

### 4.4 Маппинг Frontol → PrismaLite
| Frontol | event_code |
|---------|------------|
| AddItem | 20 |
| VoidItem | 23 |
| QtyChg | 25 |
| Mark | 27 |
| Payment | 70/73 |
| Total | 90 |
| Fiscal | 92 |

### 4.5 Нормализация
1. Преобразование логов в JSON.
2. Поля → стандартные: `cashier`, `pos`, `timestamp`, `payload`.
3. ТЗ по времени: все значения → UTC, учитывать локальный часовой пояс магазина.
4. События маппятся на коды Set Retail.
5. Служебные события (`Start`, `Stop`, `CashIn`, `CashOut`) → отдельный тип.

## 5. Другие POS / универсальные требования

- Любые сторонние POS должны предоставлять события с минимум полями: `timestamp`, `cashier`, `pos`, `event_code`, `payload`.
- Необходима синхронизация времени (NTP).
- Поддержка передачи пакетов (batch) и realtime.
- Подпись/шифрование (по возможности) или VPN-туннели.

## 6. Dead-letter Queue (DLQ)

- Несовместимые/битые события попадают в DLQ (Kafka topic / очереди).
- Параметры DLQ:
  - оригинальный payload;
  - причина (validation error, mapping error);
  - число попыток.
- От DLQ события может быть возвращено на повторную обработку после исправления.

## 7. Ошибки интеграций

### 7.1 Set Retail
- Неверный XML (невалидный синтаксис).
- Отсутствующие обязательные поля (например, `TS`).
- Неподдерживаемый код события.

### 7.2 Frontol
- Повреждённые строки логов.
- Дублирование (повторное воспроизведение).
- Несогласованный часовой пояс.

### 7.3 Общие
- Событие вне рабочей смены (расхождение времени).
- Несвязанные DOC_BEGIN/DOC_END.
- Конфликт версии агента.

Каждая ошибка логируется с деталями и, при необходимости, вызывает alert.

## 8. POS Agent

- Принимает данные на стороне магазина, буферизует при отсутствии связи (offline buffer).
- Поддерживает режимы:
  - File watcher (Frontol logs).
  - HTTP/HTTPS push (Set Retail JSON).
  - gRPC/WebSocket (расширения).
- Параметры конфигурации:
  - `backend_url`, `tenant_id`, `store_id`.
  - Тип интеграции (`setretail`, `frontol`, `custom`).
  - Retry/backoff (5 попыток по умолчанию).
- Логи агента: `/logs/agent/*.log`, формат JSON.

## 9. Требования к интеграторам

- Синхронизация времени касс с NTP.
- Очистка/кодировка специальных символов в payload.
- Указание timezone магазина в конфигурации.
- Регулярное тестирование отправки (`agent --test`).
- Использование защищённых каналов (TLS/VPN).
- Обновление агента при релизах (через автодеплой или пакет).

## 10. Pipeline событий и связи с БД

1. Событие → `events` (партиционированное хранение).
2. Одновременное обновление `checks` (начало/конец чека).
3. Публикация в Rules Engine (stream).
4. Привязка к `video_links` по timestamp.
5. Возможность обратного экспорта (например, в внешние DWH).

## 11. Monitoring интеграций

- Метрики:
  - `ingest_events_total` (per source).
  - `ingest_failures_total`.
  - `agent_offline_seconds`.
  - Очередь (buffer) агента.
- Алерты:
  - Нет событий от кассы > X минут.
  - DLQ рост > threshold.
  - Ошибки нормализации > threshold.

## 12. Открытые вопросы

| Тема | Вопрос | Ответственный |
|------|--------|---------------|
