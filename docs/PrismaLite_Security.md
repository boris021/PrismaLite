# PrismaLite_Security

## 1. Модель угроз

PrismaLite учитывает следующие угрозы:
- Неавторизованный доступ к событиям, чекам и видео.
- Подмена кассовых событий, попытки реплея.
- Меж-tenant утечки данных.
- Кража JWT/refresh токенов.
- Компрометация DVR или прямой доступ к RTSP.
- Злоупотребления привилегиями (изменение правил, удаление данных).
- SQL-инъекции, XSS, CSRF, SSRF.
- Flooding/Brute force на API.

## 2. Архитектура безопасности

Основные принципы:
- Zero Trust: сервисы имеют собственные учётные данные и минимальные привилегии.
- Все внешние соединения — только по TLS 1.2+.
- Доступ к DVR — только через backend-прокси (без прямых URL в UI).
- Журналирование и аудит всех привилегированных действий.
- Hash-chain/подпись событий (планируется для будущих релизов).

## 3. Авторизация и аутентификация

### 3.1 JWT RS256
- `POST /auth/login` выдаёт access (TTL ≤ 1 час) и refresh токены.
- Access токен подписан приватным ключом auth-сервиса; backend валидирует по публичному ключу (JWKS).
- Приватный ключ хранится в HSM/Secret Manager, ротация каждые 90 дней.
- Refresh токен — HttpOnly cookie или secure storage, привязка к IP/UA fingerprint.

### 3.2 Поток
```
[User] → creds → [Auth Service]
             ↓
        JWT (RS256)
             ↓
[Frontend] → Authorization: Bearer <token> → [Backend]
             ↓
      Backend validates via JWKS
```

### 3.3 MFA (опционально)
- Поддержка TOTP (Google Authenticator) и FIDO2 в roadmap.

## 4. Tenant Isolation

- В каждой таблице присутствует `tenant_id`.
- Backend автоматически добавляет `WHERE tenant_id IN auth_context.allowed`.
- Роли с cross-tenant правами (SuperAdmin) ограничены и аудируются.
- Видео и DVR ограничены на уровне tenant: попытки доступа к чужой камере логируются и блокируются.

## 5. ACL и роли

Пример матрицы:
```
ROLE_ANALYST:
  - events.read
  - video.read
  - incidents.write

ROLE_ADMIN:
  - users.manage
  - rules.manage
  - stores.manage
  - cameras.manage

ROLE_OPERATOR:
  - live.read
  - incidents.review
```

ACL проверяется на backend:
```python
if not acl.check(user.role, "events.read"):
    raise HTTPException(403)
```

## 6. Шифрование

- TLS 1.2+ для всех внешних API; HSTS на ingress.
- DVR каналы: RTSP over TLS (если возможно) или VPN/IPsec; иначе трафик проходит внутри закрытого сегмента.
- Хранение видео: сегменты подписаны SHA-256; опционально — AES-256 at rest.
- Конфиденциальные данные (ключи, пароли) хранятся в секрет-хранилищах (Vault/K8s Secret, Windows DPAPI).

## 7. DVR безопасность

- Backend выступает прокси: UI получает временный HLS URL вида `/video/live/{camera}?token=...`.
- Токен подписывается backend'ом, TTL ≤ 60 секунд, одноразовый.
- Ограничение количества одновременных потоков на камеру (конфигурация per tenant).
- Circuit breaker при множественных ошибках от DVR.

## 8. Аудит и логирование

- Таблица `audit_log`: фиксирует входы, изменение настроек, доступ к видео, управление инцидентами.
- Формат:
```json
{"ts":"2025-01-20T12:00:00Z","user_id":"A001","action":"video_access","store_id":5,"ip":"192.168.1.22"}
```
- Логи append-only; доступ только у security/ops.
- Алерты при событиях: доступ к чужому tenant, множественные неудачные логины, массовое удаление правил.

## 9. Защита API

- Rate limiting: 100 req/min per IP (login) и 1000 req/min default.
- Replay protection: nonce/UUID в критичных POST, timestamp в JWT, срок действия подписи ≤ 5 минут.
- Validation: Pydantic/DTO, отказ от raw SQL во frontend.
- CORS: белый список доменов; CSP `default-src 'self'`.
- CSRF для stateful (если refresh через cookie).
- Content filtering для загрузок (если появятся).

## 10. Политики паролей и секретов

- Пароли: ≥12 символов, цифры/буквы/спецсимволы, срок жизни ≤ 90 дней.
- Аккаунты блокируются после 5 неудачных логинов (временная блокировка).
- Service accounts — только с ротацией ключей (30–60 дней).
- Хранение конфигов: `.env`/секреты не попадают в VCS.

## 11. Бэкапы и восстановление

- Бэкапы PostgreSQL шифруются (pg_dump → gpg/AES).
- Ключи шифрования хранятся отдельно (KMS, offline).
- Восстановление проверяется минимум раз в квартал.
- Видеоархив: шифрование при необходимости, контроль доступа по RBAC.

## 12. Мониторинг безопасности

- Метрики:
  - `auth_failed_total`
  - `dvr_blocked_sessions`
  - `acl_denied_total`
  - `rate_limit_hits_total`
- SIEM интеграция: экспорт audit-логов в SOC (опционально).
- Alert rules: множественные логины с одного IP, резкий рост `acl_denied`, запросы к чужим tenant.

## 13. Инциденты безопасности

- Плейбук:
  1. Обнаружение (alert/SIEM).
  2. Классификация (P1/P2/P3).
  3. Изоляция (блокировка токена, отключение сервиса).
  4. Уведомление ответственных (Security Officer, Product).
  5. Анализ логов/аудита.
  6. Восстановление и постмортем.
- Хранение доказательств: неизменяемые лог-файлы, контроль целостности.

## 14. Соответствие требованиям

- GDPR/152-ФЗ: персональные данные кассиров — защита на уровне базы (шифрование, RBAC).
- PCI DSS (при работе с банковскими картами) — минимизация хранения card data, токенизация.
- Возможность расширения под SOC 2 (логирование, контроль доступа, мониторинг).
